## 1. Мета роботи

Спроєктувати контракти взаємодії компонентів E-Commerce Cloud Platform із використанням REST API на основі OpenAPI 3.0.3 та gRPC на основі Protocol Buffers. Перевірити REST-контракт за допомогою mock-сервера Prism, згенерувати Java-код gRPC-клієнта та сервера, а також порівняти розміри серіалізованих повідомлень JSON і Protobuf.

## 2. Архітектурне позиціонування API

REST API використовується як зовнішній контракт між клієнтським застосунком і Backend API. Він забезпечує стандартну HTTP-взаємодію з ресурсами замовлень, фільтрацію, створення, перегляд, оновлення та скасування замовлень.

gRPC використовується для типізованої внутрішньої взаємодії між модулем замовлень та складською системою. Unary RPC підходить для команд і запитів, а Server Streaming — для отримання послідовності подій про зміну стану операції.

## 3. REST API та OpenAPI

Специфікація: [`api/openapi.yaml`](../api/openapi.yaml).

Контракт створено за підходом Contract-First. Використано OpenAPI 3.0.3.

### 3.1. Опис endpoint-ів

| HTTP-метод | Endpoint | Призначення |
|---|---|---|
| GET | `/orders` | Отримання списку замовлень із фільтрацією та пагінацією |
| POST | `/orders` | Створення замовлення |
| GET | `/orders/{orderId}` | Отримання замовлення за ідентифікатором |
| PUT | `/orders/{orderId}` | Оновлення замовлення |
| DELETE | `/orders/{orderId}` | Скасування замовлення |

Контракт містить path-параметри, query-параметри, тіла запитів і типізовані DTO-схеми. Для полів визначено типи, обов'язковість, формати, обмеження довжини й діапазонів, enum-значення та приклади.

### 3.2. Обробка помилок

Помилки описані у форматі `application/problem+json` відповідно до RFC 7807. Передбачено HTTP-відповіді:

- `400 Bad Request` — некоректний запит;
- `401 Unauthorized` — відсутня або недійсна автентифікація;
- `404 Not Found` — ресурс не знайдено;
- `422 Unprocessable Entity` — помилка валідації вмісту запиту.

Для Problem Details визначено поля `type`, `title`, `status`, а також додаткові `detail` та `instance`.

### 3.3. Параметри фільтрації та пагінації

Для `GET /orders` передбачено:

- `status` — фільтрація за статусом замовлення;
- `customerId` — фільтрація за ідентифікатором клієнта;
- `limit` — кількість елементів на сторінці, від 1 до 100, значення за замовчуванням 20;
- `cursor` — курсор для отримання наступної сторінки.

У відповіді передбачено об'єкт `pagination` із полями `limit`, `nextCursor` та `hasNext`.

7. Контрольні питання
7.1. У чому різниця між Contract-First та Code-First?
Contract-First передбачає створення та узгодження API-контракту до реалізації програмного коду. Це дає змогу паралельно розробляти клієнтську та серверну частини. Code-First починається з реалізації програмних інтерфейсів, після чого контракт генерується на основі коду.
7.2. Що таке Varint і Field Key у Protobuf?
Varint — спосіб кодування цілих чисел змінної довжини. Менші значення займають менше байтів. Field Key об'єднує номер поля та wire type за формулою:

key = (field_number << 3) | wire_type

Це дає змогу декодеру визначати тип і призначення поля у бінарному повідомленні.
7.3. Чому в proto3 немає required і як забезпечується сумісність?
У proto3 немає ключового слова required, що спрощує еволюцію схем і сумісність версій. Для сумісності не можна повторно використовувати номери видалених полів. Їх потрібно резервувати за допомогою reserved. Нові поля додають із новими номерами, зберігаючи попередні номери та типи полів.
7.4. Які основні поля RFC 7807 і чому { "error": "text" } є небажаним форматом?
Основні поля Problem Details: type, title, status. Додатково використовують detail та instance. Стандартизований формат забезпечує однакову структуру помилок для клієнтів. Об'єкт { "error": "text" } не визначає стандартизованих полів для типу, HTTP-статусу та деталізації проблеми, тому ускладнює універсальну машинну обробку.
7.5. Які переваги HTTP/2 порівняно з HTTP/1.1?
HTTP/2 підтримує мультиплексування кількох потоків в одному TCP-з'єднанні, що зменшує блокування запитів на рівні HTTP. Також HTTP/2 використовує HPACK для стиснення заголовків. HTTP/1.1 має обмеженіші можливості паралельної обробки запитів у межах одного з'єднання.
8. Висновки
У лабораторній роботі спроєктовано REST API-контракт OpenAPI 3.0.3 та gRPC-контракт на основі Protocol Buffers для E-Commerce Cloud Platform. Для REST API описано операції роботи із замовленнями, DTO-схеми, параметри фільтрації та пагінації, а також помилки у форматі RFC 7807.

Контракт перевірено за допомогою Spectral і Prism. Успішно виконано позитивний POST-тест із HTTP 201, негативний POST-тест із HTTP 422 та GET-тест із HTTP 200. Для внутрішньої взаємодії описано Unary та Server Streaming RPC. Java stubs згенеровано засобами Maven і успішно скомпільовано.

За результатами benchmark розмір Protobuf-повідомлення становив 273 байти проти 656 байтів для JSON UTF-8, що відповідає скороченню на 58,38% для використаної тестової сутності.

Отримані результати демонструють доцільність використання REST для зовнішніх API та gRPC/Protobuf для типізованої внутрішньої міжсервісної взаємодії.
