# Звіт з лабораторної роботи №5
## Розробка системи на основі архітектури, керованої подіями (Event-Driven Architecture)

**Дисципліна:** Проєктування архітектури, специфікація та стандарти інженерії  
**Тема проєкту:** E-Commerce Cloud Platform  
**Виконав(ла):** О.В. Бєльченко  
**Група:** 3ПР1  
**Заклад:** Херсонський національний технічний університет  

## 1. Мета роботи

Мета роботи — реалізувати взаємодію компонентів системи за принципами Event-Driven Architecture (EDA), забезпечити асинхронну доставку подій, незалежну роботу споживачів та ідемпотентну обробку повторно доставлених повідомлень.

## 2. Архітектурне рішення

Для наявного проєкту E-Commerce Cloud Platform реалізовано асинхронну шину подій InMemoryEventBus. Вона використовує ExecutorService та пул потоків для незалежного запуску обробників.

Взаємодія побудована за схемою:

```text
CreateOrderUseCase
       |
       | IEventPublisher
       v
  InMemoryEventBus
       |
       +--------------------------+
       |                          |
       v                          v
StockReservationConsumer   OrderNotificationConsumer
       |                          |
       v                          v
ProcessedEventStore        ProcessedEventStore


Для подій оплати передбачено окремого споживача PaymentAuditConsumer.

Шина відповідає за маршрутизацію та асинхронний запуск обробників. Бізнес-логіка залишається всередині споживачів.
3. Каталог подій
ПодіяПризначенняОсновні дані
OrderCreatedEventФіксує створення замовленняEventId, OccurredAt, AggregateId, CustomerId, TotalAmount, ItemCount
PaymentProcessedEventФіксує успішну обробку платежуEventId, OccurredAt, AggregateId, PaymentId, Amount, PaymentMethod

Події реалізовані як Java records. Їхні поля є незмінними. Кожна подія має унікальний UUID, час виникнення у форматі Instant (UTC) та ідентифікатор агрегату.
4. Публікація подій
У шарі Application створено порт IEventPublisher. Сценарій CreateOrderUseCase не залежить від конкретної реалізації шини.

Після успішного збереження замовлення репозиторієм сценарій формує OrderCreatedEvent і передає її через IEventPublisher.

Таким чином, подія публікується лише після успішного збереження замовлення. Якщо перевірка складських залишків або збереження завершується помилкою, подія не публікується.
5. Споживачі подій
Реалізовано три незалежні компоненти:
1. StockReservationConsumer — обробляє створення замовлення та виконує логіку резервування товарів.
2. OrderNotificationConsumer — обробляє ту саму подію незалежно від першого споживача та імітує надсилання повідомлення клієнту.
3. PaymentAuditConsumer — обробляє PaymentProcessedEvent та реєструє факт успішної оплати.
Перші два споживачі підписані на OrderCreatedEvent. Вони запускаються асинхронно та не викликають один одного.

Помилка окремого обробника перехоплюється шиною. Вона не перериває виконання інших обробників і не змінює результат уже виконаного сценарію створення замовлення.
6. Ідемпотентність
Для захисту від повторної доставки створено InMemoryProcessedEventStore.

Сховище зберігає пару ідентифікаторів: назву споживача та EventId. Метод executeOnce синхронізує перевірку, виконання дії та реєстрацію успішної обробки.

Якщо той самий споживач отримує ту саму подію повторно, бізнес-дія не виконується вдруге. Різні споживачі мають незалежні записи обробки, тому кожен із них може самостійно обробити одну подію.

У разі помилки бізнес-дії ідентифікатор не позначається як успішно оброблений.
7. Перевірка роботи
Автоматизовані тести перевіряють:
- публікацію OrderCreatedEvent після успішного збереження замовлення;
- відсутність публікації при помилці перевірки товарних залишків;
- незалежне виконання двох споживачів однієї події;
- повторну доставку тієї самої події без повторної зміни стану;
- ізоляцію помилки одного споживача;
- доставку PaymentProcessedEvent окремому споживачу.
Під час демонстраційного тесту одна подія публікується двічі. Очікуваний результат: резервування та повідомлення обробляються по одному разу, хоча кожен обробник отримує два виклики. Третій тестовий обробник навмисно генерує помилку, але інші обробники завершують роботу.

Фактичний результат тестового запуску збережено у файлі docs/lr5-demo.log.
8. Відповіді на контрольні запитання
1. Які переваги асинхронної взаємодії через події порівняно із синхронними HTTP-викликами?

Асинхронна взаємодія зменшує зв'язність між компонентами. Видавець не повинен знати, скільки існує споживачів і як саме вони реалізовані. Обробники можуть виконуватися незалежно, а тимчасова помилка одного споживача не обов'язково блокує інших. Це полегшує масштабування та додавання нових функцій.

2. Що таке ідемпотентність споживача та як її реалізовано?

Ідемпотентність означає, що повторна обробка одного повідомлення не призводить до повторного виконання бізнес-операції. У роботі використовується EventId разом з ідентифікатором споживача. Перед виконанням дії сховище перевіряє, чи оброблялася ця пара раніше. Повторна доставка пропускається без зміни стану.

3. Чим відрізняється брокер повідомлень від Mediator?

Брокер повідомлень зазвичай забезпечує незалежну доставку повідомлень між процесами або сервісами, часто з використанням мережевого транспорту та механізмів збереження повідомлень. Mediator координує взаємодію об'єктів переважно всередині одного застосунку. У цій роботі використано локальну асинхронну шину, яка демонструє принципи підписки та доставки подій, але не замінює повноцінний розподілений брокер.
9. Висновки
У ході лабораторної роботи реалізовано базову подійну архітектуру для E-Commerce Cloud Platform. Сценарій створення замовлення публікує незмінну подію через порт Application. Асинхронна шина доставляє її незалежним споживачам. Для захисту від повторної доставки реалізовано сховище оброблених ідентифікаторів подій.

Автоматизовані тести перевіряють повторну доставку, незалежність споживачів, ізоляцію помилок і публікацію подій після успішного виконання сценарію.
10. Обмеження реалізації
Використане сховище подій та ідемпотентності є потокобезпечними структурами в пам'яті одного процесу. Після перезапуску застосунку вони не зберігають стан. Для промислового розгортання потрібен зовнішній брокер повідомлень і постійне сховище оброблених подій. У межах лабораторної роботи ці механізми не є предметом реалізації.
